# Swift AuthProvider parity plan (roaming authenticators + PRF-secret integrity)

## Context

Kotlin's `SirosWallet.createAuthProvider()` defaulted to `LocalAuthProvider` (a from-scratch,
no-roaming-support WebAuthn implementation) instead of `CredentialManagerAuthProvider` (which
delegates to the OS and supports roaming authenticators). We flipped that default given SIROS
ID's core principle: passkeys — including full roaming-authenticator support — protect private
data via a PRF-derived secret, independent of the pluggable `siros-wscd-manager` (which only
protects credential-signing keys, not this secret).

A background Plan agent audited the Swift SDK for the analogous gap. Findings below.

## Findings

1. **No SDK-level default/config switch exists in Swift** (unlike Kotlin's `createAuthProvider()`
   + `WalletConfig.useSystemCredentialManager`). The caller constructs and injects whichever
   `AuthProvider` it wants via `SirosWallet.init(authProvider:)`.

2. **iOS's actual default is sound**: `SampleApp/Sources/WalletViewModel.swift:594-600` uses
   `#if os(iOS)` → `ASAuthorizationAuthProvider`, `#else` → `LocalAuthProvider`. So on iOS — the
   SDK's primary target — the real, OS-backed passkey provider is already the default. This part
   does NOT have Kotlin's original problem (defaulting to the weak local provider).

3. **macOS gap**: `Package.swift` lists `.macOS(.v13)` as a supported platform, but
   `Sources/SirosAuth/ASAuthorizationAuthProvider.swift` is hard-gated `#if os(iOS)` even though
   `@available(iOS 16.0, macOS 13.0, *)` and `ASAuthorizationPlatformPublicKeyCredentialProvider`
   itself both support macOS 13+. So macOS silently falls back to unprotected, in-memory
   `LocalAuthProvider` with no real device authentication at all.

4. **Roaming-authenticator gap confirmed (the direct Kotlin analog)**: `ASAuthorizationAuthProvider`
   only ever builds requests from `ASAuthorizationPlatformPublicKeyCredentialProvider` (lines
   39-41, 66-68) and hands a single request to `ASAuthorizationController` (lines 110-124).
   `grep -rn "SecurityKey"` across `Sources/` and `SampleApp/` returns nothing — the SDK never
   constructs an `ASAuthorizationSecurityKeyPublicKeyCredentialProvider` request (Apple's
   mechanism for USB/NFC/BLE FIDO2 security keys). **There is currently no way to use a roaming
   security key with this SDK on any platform** — exactly analogous to Kotlin's pre-fix
   `LocalAuthProvider` having no CTAP2 support.

5. **`LocalAuthProvider` does NOT have Kotlin's exact bug** (verified by reading the code, not
   assumed): its `register()` (lines 68-71) creates the `SecKey` with a plain attributes dict —
   no `kSecAttrAccessControl`, no biometry flag at all — and `signWithKey()` (lines 276-287) calls
   `SecKeyCreateSignature` directly with no `LAContext`. Since no access-control is attached to
   the key, there's nothing for iOS to silently fail to prompt for — signing always succeeds.
   This is a *different*, arguably worse property: zero device-authentication guarantee, by
   design, silently (it's documented as dev/test-only, but is still what ships as the runtime
   fallback on non-iOS platforms today).

6. **Separate, more severe bug found while reading (flagging for visibility — not in original
   scope, but directly undermines the stated PRF-secret principle right now)**: `SirosWallet.swift`
   calls `authProvider.getPrfOutput(credentialId: Data(), salt: ...)` at all three call sites
   (register: line 329, login: line 444, unlock: line 598) — passing an **empty `Data()`** instead
   of the actual `result.credentialId`. `ASAuthorizationAuthProvider.getPrfOutput()` (lines 94-106)
   doesn't request Apple's real PRF extension at all (its own comment: "iOS 18+ adds some PRF
   support... but availability varies. For now, derive locally using HKDF") and instead computes
   `HKDF(ikm: SymmetricKey(data: credentialId), salt: salt)`. With `credentialId` always empty,
   the secret protecting private data on iOS today is `HKDF(ikm: empty, salt: prfSalt)` — derived
   from data that isn't secret and isn't gated by Face ID/Touch ID at all. This silently
   undermines "PRF-derived secret protects private data" on the SDK's actual default path, and
   never surfaces as an error — arguably the most urgent item here.

## Plan

### A. Roaming-authenticator support (primary analog of the Kotlin gap)
In `Sources/SirosAuth/ASAuthorizationAuthProvider.swift`, add a second request built from
`ASAuthorizationSecurityKeyPublicKeyCredentialProvider(relyingPartyIdentifier:)` for both
`register()` and `authenticate()`, and pass `[platformRequest, securityKeyRequest]` into a single
`ASAuthorizationController(authorizationRequests:)` in `performRequest()` (lines 110-124),
matching Apple's documented combined platform+security-key pattern.
`authorizationController(didCompleteWithAuthorization:)` (line 128) needs a type-switch
(`as? ASAuthorizationPlatformPublicKeyCredentialAssertion` vs
`as? ASAuthorizationSecurityKeyPublicKeyCredentialAssertion`) since the returned credential type
now varies. Recommend default-on (mirroring Kotlin's "roaming support is the default" decision),
not an opt-in flag.

### B. macOS parity gap
Remove the `os(iOS)` restriction in `ASAuthorizationAuthProvider.swift`'s guard (the
`@available(iOS 16.0, macOS 13.0, *)` annotation already claims macOS support), so macOS gets a
real passkey provider instead of silently falling back to unprotected `LocalAuthProvider`. Update
`SampleApp/Sources/WalletViewModel.swift:594-600` to use `ASAuthorizationAuthProvider` on macOS
too (with an `NSWindow`-based anchor), demoting `LocalAuthProvider` to an explicit, clearly-labeled
opt-out — not a silent per-platform default.

### C. `LocalAuthProvider` biometric-ceremony fix
Needed regardless of default, per the Kotlin precedent of fixing it even though it's not the
primary path: add `kSecAttrAccessControl` with `.biometryCurrentSet`/`.userPresence` to the
key-generation attributes in `register()` (lines 68-76), and thread an `LAContext` through
`signWithKey()` (lines 276-287) via `kSecUseAuthenticationContext`, so `LocalAuthProvider` actually
enforces device authentication if ever used as a real (non-dev) fallback, rather than silently
providing none. Add a test in `Tests/SirosAuthTests/` asserting signing fails/prompts without
authorization.

### D. PRF-derivation fix (higher severity — recommend doing this first/independently)
Fix the three `getPrfOutput(credentialId: Data(), ...)` call sites in
`Sources/SirosWallet/SirosWallet.swift` (lines 329, 444, 598) to pass the real
`result.credentialId`, and implement real PRF extraction in `ASAuthorizationAuthProvider` using
`ASAuthorizationPublicKeyCredentialPRFRegistrationInput`/`PRFAssertionInput` (iOS 18+), with the
current HKDF-of-credentialId retained as an explicit, documented weaker fallback only for
pre-iOS-18 devices — not the unconditional path it is today.

## Critical files
- `Sources/SirosAuth/ASAuthorizationAuthProvider.swift`
- `Sources/SirosAuth/LocalAuthProvider.swift`
- `Sources/SirosWallet/SirosWallet.swift` (lines 329, 444, 598 for item D)
- `Sources/SirosWallet/WalletConfig.swift` (if adding an explicit opt-out flag, mirroring Kotlin's
  `useSystemCredentialManager`)
- `SampleApp/Sources/WalletViewModel.swift:594-600`

## Suggested priority order
1. **D (PRF-derivation fix)** — silently undermines the core security principle today, on the
   default path, with no error surfaced. Highest severity despite being outside the original
   "roaming authenticator" scope.
2. **A (roaming-authenticator support)** — the direct analog of the Kotlin fix; currently a
   hard capability gap, not a silent correctness bug.
3. **B (macOS parity)** — real gap but macOS is a secondary target.
4. **C (`LocalAuthProvider` biometric ceremony)** — lowest priority; only matters if that
   fallback is ever used for anything beyond dev/test, which it's explicitly documented not to be.
